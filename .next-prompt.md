## The established pattern (reuse it exactly)
- `DataHandler.defer_db(fn, *args)` runs `fn` in the reactor thread pool, returns a Deferred
  whose callbacks fire back on the reactor thread.
- `DataHandler._run_db` owns the worker's scoped session (commit/rollback/close) and **retries**
  the whole unit on transient serialization errors (deadlock 1213, lock-wait 1205,
  record-changed 1020) from a fresh session. CONSEQUENCE: a worker fn must be ONE uncommitted
  transaction — never call the self-committing `userdb` helpers (they commit internally, so a
  retry would re-apply earlier writes). Issue raw `sess().add/.delete` and let `_run_db` commit.
  Do NOT treat a duplicate as a retry — a 1062 IntegrityError is NOT in the retry set; catch it
  inside the worker, `sess().rollback()`, and return a verdict tuple (see `do_register_insert`).
- **Split rule:** worker = PURE DB I/O returning plain data (ids/tuples/OfflineClient snapshots)
  — NEVER a live ORM row, NEVER touching shared in-memory state (`clients`/`usernames`/
  `user_ids`/`channels`/`battles`, the 1.1 ban cache, the 1.2 offline-user cache, or a client's
  in-memory dicts). Reactor-thread callback = ALL shared-state mutation + caches + all `client.Send`.
- A callback runs OUTSIDE `dataReceived`'s per-request session guard. If the callback does ANY
  reactor-side DB, bracket it with `session_manager.commit_guard()/rollback_guard()/close_guard()`
  (see `_login_finish`, `_register_inserted`, `_ignorelist_send`). If it does NO DB (only memory +
  Send), no bracket (see the friend callbacks, `_end_session_done`, `_ingame_time_saved`).
- `clientFromID(id, True)` / `clientFromUsername(.., True)` can do a reactor-side DB query AND a
  1.2-cache write on a miss — treat them as DB. From a worker they are FORBIDDEN (cache write is
  cross-thread). Use cache-free worker resolvers (`_user_id_from_username`, `_user_access_from_username`).
- No new locks: reactor callbacks are serialized, so re-check invariants in the callback. Guard
  `client.session_id in self._root.clients` at the top of every callback that touches the client
  (client may disconnect mid-DB). On the worker errback, do NOT mutate shared state (write didn't happen).
- For check-then-act where the reactor re-check can still race the write (no unique constraint /
  insert), prefer ONE atomic worker unit + tolerate the residual race (tolerant delete, or
  IntegrityError handling for inserts — RENAMEACCOUNT in your group reuses the REGISTER technique).

## Critical cautions
- Each worker returns plain data; a detached ORM row from one session is unusable elsewhere.
- Keep cache/in-memory invalidation (1.1 ban cache, 1.2 user cache, per-client dicts) on the
  reactor thread (in the callback).
- Convert ONE handler group (or sub-slice) per PR. Small incremental PRs.
